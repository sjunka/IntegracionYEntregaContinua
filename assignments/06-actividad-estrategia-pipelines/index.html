Respuestas rápidas

1. ¿Cuántos repositorios y qué versiona cada uno?

4 repos: repo-backend la API + pruebas + Dockerfile + migraciones (Flyway); repo-frontend la web; repo-infra el Terraform de staging y producción; repo-e2e las pruebas de punta a punta.

Por qué las migraciones van con el backend: la versión X del API necesita el esquema Y. En el mismo repo viajan juntas y no hay que coordinar dos pipelines. Un repo de BD aparte solo compensa si varios servicios comparten la BD.

Costo: coordinar front y back (lo cubre el contrato con Pact). Alternativa: monorepo, más fácil de coordinar pero con pipelines más pesados.

2. ¿Qué estrategia de ramificación?

GitHub Flow + tags: main siempre desplegable; ramas cortas (feature/*, fix/*) que vuelven por PR en 1-2 días; un tag semver (v1.4.0) marca qué sale a producción. Un error urgente es otra rama corta desde main.

Por qué: se integra a main todos los días, que es lo que pide CI. El control de la salida ya lo dan el tag y la aprobación manual, así que una rama release/* sobraría. Costo: main debe estar siempre verde; lo sin terminar se esconde con feature flags. Alternativa: GitFlow, con más control por versión pero integración menos frecuente.

3. ¿Qué pipelines y en qué repos?

Back y front tienen su pipeline de CI en cada PR (GitHub Actions). El pipeline de CD despliega a staging en cada merge a main, y a producción cuando hay tag y alguien aprueba (GitHub Environments). repo-infra corre terraform plan en el PR y apply al hacer merge. repo-e2e lo invoca el CD contra staging.

Las migraciones corren antes de desplegar el backend, en el mismo pipeline.

4. ¿Qué etapas en CI, cuáles en CD y por qué?

CI: lint → unitarias (y de componentes en el front) → integración con BD (Testcontainers) → contrato (Pact) → quality gate de Sonar → escaneo de seguridad (SAST, dependencias) → build y publicar imagen. No necesitan ambiente desplegado: el error se atrapa en el PR (fail fast).

CD: migrar BD (expand) → deploy a staging → E2E y smoke → aprobación manual → canary 5% → monitoreo con rollback automático. Necesitan un ambiente real con todo integrado.

Regla clave: se construye una sola vez. La imagen que pasó staging (mismo digest) es la que se etiqueta y va a producción.

5. ¿Despliegue continuo o entrega continua?

Entrega continua. Todo queda listo para producción, pero una persona aprueba el último paso. Razones: hay pagos, las migraciones de BD no siempre se revierten, y el error en reservas cuesta dinero.

Para bajar el riesgo: canary + rollback automático si suben los errores.

Definiciones de bolsillo

  • CI: integrar el código a main varias veces al día, validado por build y pruebas automáticas.
  • Entrega continua: cada cambio queda listo para producción; salir es decisión humana.
  • Despliegue continuo: cada cambio que pasa las pruebas sale solo a producción.
  • Artefacto: el resultado del build (imagen Docker, .jar) con versión, inmutable.
  • Canary: la nueva versión le llega primero a un % pequeño de usuarios.
  • Blue-green: dos ambientes iguales; se cambia el tráfico de uno al otro de golpe.
  • Rollback: volver a la versión estable anterior.
  • Expand/contract: migrar la BD en pasos compatibles para que la versión vieja siga funcionando. Es lo que permite el rollback con migraciones.
  • Prueba de contrato: verifica que front y back cumplen el mismo acuerdo de API sin desplegar nada (Pact).
  • Quality gate: regla que bloquea el PR si baja la cobertura o aparecen bugs (Sonar).
  • Feature flag: activar o apagar una funcionalidad sin redesplegar.
  • Métricas DORA: frecuencia de despliegue, lead time, tasa de fallos y tiempo de recuperación.
